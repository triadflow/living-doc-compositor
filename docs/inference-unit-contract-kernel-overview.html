Architecture overview

A contract kernel for scoped inference units

The useful idea is not that the harness is vaguely like an operating system. The useful idea is that the harness separates model claims from lifecycle authority, then makes that separation explicit enough to guide implementation.

Core rule

An inference unit may produce claims. The harness must produce authority. A unit can say it changed files, recommends repair, approves closure, or needs continuation. The controller validates contracts, snapshots evidence, checks gates, chooses the next unit, and writes terminal state.

The real boundary is claim versus authority

The microkernel language is useful only if it preserves this boundary. The model-facing unit is allowed to reason inside a role. The harness is the authority that decides what counts, whether the next transition is legal, and whether the lifecycle can stop.

Kernel authority

controller decision
Evidence snapshot
Controller records git state, required hard facts, proof gates, artifacts, and trace references.

Closure-review plus proof gates authorize terminal closure; the controller writes terminal state.
Side-effect gate
Source changes require commit evidence. Configured PR policy requires PR-review evidence before closure.
Next scheduled unit
The selected unit must be registered, allowed for the run, and legal after the current unit.

The lifecycle is message passing, not direct agent chaining

A unit does not own the next call. It emits a typed result. The harness turns that result and the frozen evidence into the next controlled input. That makes every transition visible, replayable, and testable.

01 input

Objective state

Living doc path, objective, success condition, required inspection paths, and run policy.

02 unit

Scoped inference

Worker, reviewer, repair, continuation, commit-intent, PR-review, or closure-review.

03 contract

Typed output

Result schema, verdict, basis, artifacts, side-effect intent, and next recommendation.

04 validate

Kernel validation

Input and output contracts, allowed verdicts, required fields, and required inspections.

05 evidence

Controller facts

Git state, proof gates, changed files, PR policy, trace refs, and hard facts snapshot.

06 schedule

Next unit

Selection is checked against the registry and run-allowed unit set before execution.

07 terminal

Closure or continue

Only the closure path can authorize final terminal state. Other outcomes route onward.

Why this guides future work

Any new capability should enter as a registered unit, a gate, or a controller-owned evidence detector. If it bypasses those surfaces, it is probably weakening the architecture.

What makes this stronger than a big agent loop

The strength is operational. Failures can be localized to a contract, gate, artifact, scheduler decision, or terminal authorization path instead of being collapsed into "the agent decided wrong."

Separation of powers

Worker does work. Reviewer judges evidence. Closure-review authorizes final closure. The controller persists terminal state. Each role is narrow enough to inspect and replace.

Replayable proof surface

The harness writes prompts, input contracts, raw JSONL events, result artifacts, validation artifacts, evidence bundles, and terminal state. The run is not just a transcript.

Policy before persuasion

The next unit cannot be chosen only because a model asks for it. It must be registered, allowed by run config, and legal after the current unit type.

Closure is explicit

A closure-sounding reviewer verdict is not enough. Terminal closure requires the closure path, side-effect gates, hard facts, and terminal-state write.

How this should guide future work

The architecture gives a practical test for every proposed feature. Decide whether it belongs in a unit, a gate, an evidence detector, a scheduler rule, or an observation surface.

1

Add behavior as units when it reasons

If the new behavior interprets evidence or makes a judgment, register a unit with a narrow role, typed input, typed output, allowed verdicts, and legal next units.

2

Add gates when it grants authority

If the behavior decides whether closure, commit, PR review, or lifecycle continuation is allowed, make it a controller-owned gate with inspectable evidence.

3

Add detectors when it records facts

If the behavior captures git state, proof routes, rendered artifacts, trace refs, file existence, or policy state, keep it outside the model and snapshot it.

4

Split iteration by authority surface

When living-doc-harness-iteration.mjs grows, extract by kernel service: gate evaluator, next-unit selector, side-effect gate runner, proof builder, evidence publisher.

5

Keep dashboards observational

The dashboard should display contracts, artifacts, graph state, and terminal results. It should not become a hidden decision-maker or a second lifecycle controller.

6

Treat bypasses as design smells

A unit directly invoking the next unit, persisting closure, or making unvalidated side effects is a breach of the kernel boundary unless explicitly modeled.

A sharper vocabulary

"Microkernel" is a good shorthand, but the implementation vocabulary should be more precise when you are designing code.

Use this phrase publicly

The harness is a contract kernel for inference units.

Units run in scoped roles, emit typed outputs, and may only recommend transitions.
The kernel validates contracts, records evidence, evaluates gates, schedules
the next unit, and owns terminal lifecycle state.
